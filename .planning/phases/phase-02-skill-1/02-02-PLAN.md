Create `~/.claude/skills/okr-goal-setting/workflows/step2-smart-validate.md` — the SMART validation workflow step.

This file guides the Claude Code agent through validating a user's draft OKR objective against the 5 SMART dimensions using LLM intelligence (D-05).

Required content:

1. **Input**: The user's draft Objective title and description (from Step 1 or user-provided).

2. **SMART dimension analysis procedure**: For each of the 5 dimensions, the agent must perform LLM-based analysis and output in this exact format:

```
**{Dimension Chinese Name} — {Result}**

当前状态: {1-2 sentence description of current state}
{问题原因: 如果Result为"问题"，说明原因}
改写示例:
1. {rewritten version 1}
2. {rewritten version 2 (optional)}
```

Dimension mapping (Chinese name + criteria for LLM):

- **Specific（具体性）**: Is the objective clear and specific? Vague goals like "improve quality" fail. Good goals specify what, for whom, and how. Result = "通过" if specific, "问题" if vague.
- **Measurable（可衡量性）**: Can progress be measured quantitatively? Goals without numbers/metrics fail. Example: "提升系统稳定性" → should be "SLO 达到 99.9%" or "月度 P0 故障 ≤ 1 次". Result = "通过" if measurable, "问题" if not.
- **Achievable（可实现性）**: Is the goal realistic given resources and time? Overly ambitious or trivial goals fail. Consider the user's historical average score from Step 1. Result = "通过" if reasonable, "问题" if unrealistic.
- **Relevant（相关性）**: Does the goal align with team/company priorities? Does it contribute to the user's role responsibilities? Result = "通过" if relevant, "问题" if disconnected.
- **Time-bound（时限性）**: Does the goal have a clear deadline or milestone dates? OKR cycles provide implicit timeboxing, but specific milestones are better. Result = "通过" if time-bound, "问题" if open-ended.

3. **LLM prompt design** (D-05): Include a prompt template that the agent uses to analyze each dimension. The prompt must:
   - Take the objective title + description as input
   - Include the dimension definition and evaluation criteria
   - Include the user's historical OKR data (from Step 1) for context
   - Output structured result with: status (通过/问题/建议), current state description, problem reason (if applicable), 1-2 rewritten examples

4. **Summary table**: After analyzing all 5 dimensions, output a Markdown table:
```
| 维度 | 结果 | 简要说明 |
|------|------|----------|
| Specific | 通过/问题/建议 | 一句话说明 |
| Measurable | 通过/问题/建议 | 一句话说明 |
| Achievable | 通过/问题/建议 | 一句话说明 |
| Relevant | 通过/问题/建议 | 一句话说明 |
| Time-bound | 通过/问题/建议 | 一句话说明 |
```

5. **Overall SMART score**: Count 通过 as 1 point, 建议 as 0.5, 问题 as 0. Display as "SMART评分: X/5".

6. **Continue prompt** (D-01): End with "是否继续到 Step 3 (对齐检查)? 回复'继续'。"

7. **Output format** (D-02): All output is plain text + Markdown tables. No code blocks, no JSON, no Feishu cards.

8. **Example output** for Measurable dimension (include as reference):
```
**Measurable（可衡量性）— 问题**
「提升系统稳定性」无法量化。建议改为「SLO 达到 99.9%」或「月度 P0 故障 ≤ 1 次」
```

The rewrite examples must be concrete and directly usable by the user, not abstract suggestions.

Create `~/.claude/skills/okr-goal-setting/workflows/step3-alignment-check.md` — the alignment check workflow step.

This file guides the Claude Code agent through checking the user's draft OKR against their manager's OKRs and peer team dependencies.

Required content:

1. **Input**: 
   - User's draft Objective title and description
   - User's userID (from Step 1)
   - SMART validation results (from Step 2, for context)

2. **Data fetching procedure**:
   a. Call `lark-cli okr alignments --objective-id {userObjectiveId}` to fetch existing alignment relationships.
   b. For each alignment returned, call `lark-cli okr objectives get --id {targetObjectiveId}` to get the target objective's details (title, owner, description).
   c. If no alignments exist in the system, attempt to find the user's manager by calling `lark-cli okr cycle-list --user-id {userID}` and checking for higher-level objectives in the same department.
   d. For peer dependencies, search for OKRs from other teams in the same cycle that might have dependency relationships (based on keyword overlap in titles/descriptions).

3. **Alignment classification** (D-08): For each alignment found, classify and output:

**贡献型对齐** (Contributing): The user's objective contributes to a higher-level or peer objective.
Format:
```
**贡献型对齐**：你的目标「{user's objective title}」有助于 {target owner name} 的目标「{target objective title}」达成
追问建议：{specific follow-up question, e.g., "你计划如何量化对这个目标的贡献？"}
```

**依赖型对齐** (Dependent): The user's objective depends on another team or person completing their objective first.
Format:
```
**依赖型对齐**：你的目标「{user's objective title}」需要 {target owner name} 的「{target objective title}」完成后才能推进
追问建议：{specific follow-up question, e.g., "你是否和 {target owner name} 确认过他们的交付时间？"}
```

4. **Output format**:
   - Section 1: 贡献型对齐 list (0 or more items)
   - Section 2: 依赖型对齐 list (0 or more items)
   - Section 3: 未覆盖的上级目标 (any manager objectives not aligned to)
   - Each item includes: target owner name, target objective title, specific follow-up question

5. **Summary**: If no alignments found, display: "未检测到对齐关系。建议手动确认：1) 你的目标是否有助于上级的某个目标？2) 你的目标是否依赖其他团队的某个目标？"

6. **Continue prompt** (D-01): End with "是否继续到 Step 4 (修改建议)? 回复'继续'。"

7. **Output format** (D-02): All output is plain text + Markdown tables.

8. **Example output** (include as reference):
```
**贡献型对齐**：你的目标「优化 CI/CD 流程」有助于上级目标「提升研发效率」达成
**依赖型对齐**：你的目标「完成新版 API 上线」需要平级团队「前端重构」完成后才能对接
```
