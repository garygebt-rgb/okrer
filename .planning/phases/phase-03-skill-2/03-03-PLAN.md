**Title:** Step 4: 风险识别 (Risk Detection)

**Inputs:** Per-KR comparison data from step3 (keyResultId, title, baseline, current, delta)

**Steps:**

1. **Build LLM assessment prompt:**
   Construct a prompt for Claude that includes:
   - Context: "You are assessing OKR progress for biweekly tracking. For each Key Result, evaluate whether there has been meaningful progress since the last baseline."
   - Input data: the comparison table from step3, including KR title, description, baseline score, current score, and delta
   - Instructions: "For each KR, classify as on_track (有进展) or no_progress (无进展). Provide a brief reason for each classification."

2. **LLM evaluation criteria (guidance, NOT hard rules):**
   The LLM should consider:
   - Score change: Did the score increase, decrease, or stay the same?
   - Magnitude: Is the change meaningful or negligible?
   - Direction: Is the KR trending toward or away from its target?
   - Context: Does the KR description suggest what kind of progress is expected?
   - Time: Has it been a reasonable amount of time since the last update?

   IMPORTANT: Do NOT use hardcoded numeric thresholds. The LLM should use judgment.

3. **Execute LLM assessment:**
   - Present the prompt to Claude with all KR data
   - Parse the response into per-KR risk classifications
   - Each KR gets: { keyResultId, riskLevel: 'on_track' | 'no_progress', reason: string }

4. **Build risk table:**
   Output Markdown table (per D-18):
   | 关键结果 | 风险等级 | 判断理由 |
   |----------|----------|----------|
   Where 风险等级: "有进展" (on_track) or "无进展" (no_progress)

5. **Summary:**
   - Total KRs: N
   - 有进展: X
   - 无进展: Y

6. **User confirmation:**
   - Ask: "是否继续下一步（辅导建议）？"

**Output:** Array of { keyResultId, riskLevel, reason } per KR
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| LLM prompt → Risk classification | LLM prompt injection via KR titles/descriptions containing adversarial content |
| Message preview → User confirmation | User may approve sending to wrong recipients |
| lark-cli im → Feishu IM API | Message sending requires proper scopes and recipient validation |
| config.json → Manager ID | User-configured file; invalid managerId could send to wrong person |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-09 | Spoofing | LLM risk assessment prompt | mitigate | Sanitize KR title/description inputs before including in LLM prompt — strip any content that looks like instruction override attempts (e.g., "ignore previous instructions") |
| T-03-10 | Information Disclosure | Manager message content | mitigate | Manager message includes employee's OKR progress data — only send to the verified manager ID from config.json; preview with explicit recipient display before sending |
| T-03-11 | Tampering | lark-cli im +messages-send | mitigate | Preview both messages with explicit recipient IDs; require user confirmation before executing send commands; use bot identity for employee messages (official channel) |
| T-03-12 | Denial of Service | Snapshot save after message send | mitigate | Save snapshot AFTER message send confirmation; if save fails, log error and prompt user — do not silently lose reminder state |
| T-03-13 | Spoofing | Manager ID resolution (config.json) | mitigate | Manager ID must come from user-configured config.json with managerId field (Resolved Q1); never guess or derive from OKR data alone; validate managerId format before sending; log warning if fallback (skip manager message) is used |
</threat_model>
