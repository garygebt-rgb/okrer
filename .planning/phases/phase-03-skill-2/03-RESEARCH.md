# Phase 3: Skill 2 过程跟进专家 - Research

**Researched:** 2026-04-21
**Domain:** OKR progress tracking, Feishu notification, LLM risk assessment
**Confidence:** HIGH

## Summary

Phase 3 implements the `okr-process-tracking` Claude Code Skill that provides a 5-step workflow for biweekly OKR progress tracking. It queries Feishu OKR data via `lark-cli`, compares current KR scores against locally stored baselines, uses LLM judgment for binary risk classification (on-track / no-progress), and sends differentiated notification messages to employees and managers via `lark-cli im +messages-send`.

**Key finding:** The Feishu OKR API (v2) does NOT expose a progress history endpoint through lark-cli. Each Objective/KeyResult has `score` and `update_time` fields but no historical log. This means progress comparison must be done against locally stored snapshot data, not against an API-provided history. The `ProgressSnapshot` type already exists in `okr-types.ts` for this purpose.

**Primary recommendation:** Implement the 5-step workflow as a user-triggered Claude Code Skill (user runs it manually), with local JSON file storage for progress snapshots. Phase 3 reserves the client-server registration interface but defers actual server-side cron implementation.

### Pattern 1: Local Snapshot Storage for Progress Tracking

**What:** Store KR score snapshots locally as JSON files to enable comparison across biweekly checkpoints.

**When to use:** Required because Feishu OKR API v2 does NOT provide a progress history endpoint through lark-cli.

**Implementation:**
```typescript
// Snapshot file path: ~/.claude/skills/okr-process-tracking/snapshots/{userId}-{cycleId}.json
interface ProgressSnapshot {
  snapshotId: string;
  cycleId: string;
  userId: string;
  timestamp: string;
  keyResultScores: Record<string, number>;  // keyResultId -> score
  lastReminderTimestamp?: string;           // For smart skip logic
}
```

**Load snapshot before comparison:**
```typescript
function loadSnapshot(userId: string, cycleId: string): ProgressSnapshot | null {
  const path = `~/.claude/skills/okr-process-tracking/snapshots/${userId}-${cycleId}.json`;
  if (!fs.existsSync(path)) return null;
  return JSON.parse(fs.readFileSync(path, 'utf-8'));
}
```

### Pattern 2: Differentiated Message Generation (Employee vs Manager)

**What:** Generate two different messages from the same risk data -- one friendly (employee) and one formal (manager).

**When to use:** D-15 requires both employee and manager notifications with different tones.

**Implementation:** The LLM receives the risk assessment data and a tone directive, generating separate messages:
- Employee: "你的 OKR 已经两周没更新了。建议花 5 分钟记录近期进展。"
- Manager: "[员工姓名] 的 OKR 双周跟进：3 个 KR 中 2 个有进展，1 个无进展。"

### Pattern 3: Smart Skip Logic (D-17)

**What:** If the user has updated their OKR since the last reminder, skip sending the notification.

**How:** Compare each KR's `update_time` against the stored `lastReminderTimestamp` from the previous snapshot.

```
if (all KR update_time > lastReminderTimestamp):
  // User updated since last reminder, skip
  return "智能跳过：用户在上次提醒后已更新 OKR"
```

### Anti-Patterns to Avoid
- **Do NOT hard-code risk thresholds.** D-14 explicitly requires LLM comprehensive judgment. No "score delta < 0.05 = no progress" rules.
- **Do NOT assume progress history is available from the API.** The Feishu OKR API v2 via lark-cli only returns current state. Historical comparison requires local snapshots.
- **Do NOT auto-send messages without confirmation.** The lark-im skill requires explicit user approval before sending (safety constraint). The workflow should preview messages and ask for confirmation.

## Common Pitfalls

### Pitfall 1: Missing Progress History from Feishu API
**What goes wrong:** Expecting the API to return historical score changes for KRs.
**Why it happens:** The Feishu OKR API v2 (exposed via lark-cli) returns only the current state of objectives and key results. The v1 `progress_record` API exists at `POST /okr/v1/progress_records` but lark-cli does NOT wrap it, and it requires knowing the progress_record ID (no list endpoint).
**How to avoid:** Store local snapshots after each biweekly check. Use `ProgressSnapshot` type from `okr-types.ts`.
**Warning signs:** If `loadSnapshot()` returns null, this is the first check -- treat all KRs as "baseline established".

### Pitfall 2: Message Sending Without Confirmation
**What goes wrong:** The Skill auto-sends messages to employees/managers without user review.
**Why it happens:** The lark-im skill explicitly requires user confirmation before sending (safety constraint).
**How to avoid:** Step 5 must preview both messages (employee + manager) and ask for explicit approval before executing `lark-cli im +messages-send`.
**Warning signs:** If messages are sent automatically, this violates the lark-im safety rule.

### Pitfall 3: Scope Insufficiency for IM Sending
**What goes wrong:** Message sending fails because the app lacks `im:message` or `im:message.send_as_user` scopes.
**Why it happens:** The app was configured for OKR reading only (`okr:okr.content:readonly`) but IM sending requires additional scopes.
**How to avoid:** During setup/auth check, verify IM scopes exist. If missing, guide user through `lark-cli auth login --scope "im:message"`.
**Warning signs:** `missing_scope` error on message send.

### Pitfall 4: First-Run Baseline vs Normal Check
**What goes wrong:** On first run, there's no previous snapshot to compare against, causing errors or incorrect risk assessments.
**Why it happens:** `loadSnapshot()` returns null for first-time users.
**How to avoid:** Treat first run as "baseline establishment" -- save the current state as the initial snapshot, display a message that this is the baseline, and do not send risk alerts.
**Warning signs:** `snapshot === null` should trigger a different workflow branch.

### Pitfall 5: Manager UserID Resolution
**What goes wrong:** Need to send a message to the user's manager but don't have their userID.
**Why it happens:** The OKR cycle detail includes the KR owner but not their manager. Manager info may be in the Feishu contact system.
**How to avoid:** Use `lark-cli contact +search-user` or fetch from Feishu org chart. Alternatively, the manager relationship may need to be configured manually in the skill's config.
**Warning signs:** No manager ID available -- need fallback (send to a configured group chat instead).

## Code Examples

### Loading and Comparing Snapshots
```typescript
import { ProgressSnapshot } from '../../okr-shared/okr-types';
import * as fs from 'fs';
import * as path from 'path';

const SNAPSHOT_DIR = path.join(
  process.env.HOME!, '.claude', 'skills', 'okr-process-tracking', 'snapshots'
);

function loadSnapshot(userId: string, cycleId: string): ProgressSnapshot | null {
  const filePath = path.join(SNAPSHOT_DIR, `${userId}-${cycleId}.json`);
  if (!fs.existsSync(filePath)) return null;
  try {
    return JSON.parse(fs.readFileSync(filePath, 'utf-8')) as ProgressSnapshot;
  } catch {
    return null;
  }
}

function saveSnapshot(snapshot: ProgressSnapshot): void {
  fs.mkdirSync(SNAPSHOT_DIR, { recursive: true });
  const filePath = path.join(SNAPSHOT_DIR, `${snapshot.userId}-${snapshot.cycleId}.json`);
  fs.writeFileSync(filePath, JSON.stringify(snapshot, null, 2));
}

function compareScores(
  baseline: ProgressSnapshot,
  current: Record<string, number>
): Array<{ keyResultId: string; before: number; after: number; delta: number }> {
  return Object.entries(current).map(([krId, score]) => ({
    keyResultId: krId,
    before: baseline.keyResultScores[krId] ?? 0,
    after: score,
    delta: score - (baseline.keyResultScores[krId] ?? 0),
  }));
}
```

### Sending Notification via lark-cli
```typescript
import { execSync } from 'child_process';

function sendNotification(
  userId: string,
  message: string,
  identity: 'user' | 'bot' = 'bot'
): { messageId: string } {
  const escaped = message.replace(/'/g, "'\\''");
  const result = execSync(
    `lark-cli im +messages-send --user-id "${userId}" --text '${escaped}' --as ${identity}`,
    { encoding: 'utf-8' }
  );
  return JSON.parse(result);
}
```

### Smart Skip Check
```typescript
function shouldSkipReminder(
  krUpdateTimes: Record<string, string>,  // keyResultId -> update_time (ISO timestamp)
  lastReminderTime: string
): boolean {
  // If ALL KRs were updated after the last reminder, skip
  return Object.values(krUpdateTimes).every(
    (updateTime) => new Date(updateTime) > new Date(lastReminderTime)
  );
}
```

## Open Questions (RESOLVED)

1. **Manager relationship resolution** — RESOLVED
   - **Resolution:** Phase 3 使用**本地配置文件**映射 userId -> managerUserId。在 `okr-process-tracking/` 目录下创建 `config.json`，包含 `managerId` 字段。首次运行时如果未配置，提示用户手动填入主管的飞书 userID。原因：飞书 contact API 的组织架构查询需要额外权限，Phase 3 不做服务端集成，本地配置是最简方案。
   - **Fallback:** 如果主管 userID 未配置，跳过主管端消息发送，仅发送员工端提醒。

2. **Client-server registration interface design** — RESOLVED
   - **Resolution:** 在 `okr-types.ts` 中新增 `ReminderRegistration` 类型：`{ userId, cycleId, managerId, frequency: 'biweekly', createdAt }`。创建 stub `register()` 函数写入本地 `config.json`。Phase 3 仅预留接口，不实现实际的注册/推送逻辑。服务端注册留到后续阶段。

3. **Smart skip -- what counts as "updated"?** — RESOLVED
   - **Resolution:** 检查**任意 KR 的 `update_time`** 是否晚于 `lastReminderTimestamp`。如果有任何 KR 在提醒后被更新，跳过本次提醒。理由：即使 score 未变，更新 notes/content 也表明用户有跟进行为，不需要再提醒。这比仅检查 score 变化更宽容、更简单。
